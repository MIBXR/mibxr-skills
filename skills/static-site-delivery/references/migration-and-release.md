# 迁移与发布中的易错边界

## 跟踪什么

长期维护的素材解包成普通文件并保留相对目录和校验清单。先检查同路径冲突、单文件大小和仓库体积，再选择存储方式。用户要求不用 LFS 时遵守要求；真正超过限制时提出具体替代方案，不静默丢弃素材。

Release 附件按用户选择。只发布便携包时，不把大型素材档案或技能备份 ZIP 混入。GitHub 自动提供的源码归档与手动上传附件是两类内容。

跟踪输入、包内清单、网站下载和安装说明形成内容链。说明或元数据变化也会改变 ZIP 哈希，所以大小和哈希从当前产物生成。正式图片用独立哈希关联，避免把压缩变化误判为画面变化。

## 清理历史

明确需要剔除的机器路径、用户名、账号状态、部署标识和临时凭据等。来源署名、公开参考、必要作品 slug 与依赖版本属于有意义的内容。

检查当前文件、可达历史中的文本与嵌套压缩包；媒体可能包含元数据，按实际来源检查。扫描只提供线索，不等同于保证不存在任何敏感内容。清理后解析 JSON、检查脚本参数并更新清单。

先选择历史模式。用户要求以当前状态为起点、或旧制作记录不可靠时，建立终态基线，文档描述当前源码、素材与验证，不追建或推测旧提交。只有用户需要保留且证据可靠时，才迁移可核实的旧提交顺序、作者和说明。

主线改写、标签删除、Release 替换和仓库可见性是独立范围。已有明确授权则继续；缺少会影响旧下载链接或恢复能力的决策时再确认。先备份并验证 Git refs、Release 元数据和实际附件，推送前检查远端未发生新变更。归档授权不自动等于覆盖共享历史的授权。

从清理后的可达对象建立新仓库或干净克隆，再检查要推送的 refs；仅修改工作树或查看 HEAD 不够。历史清理不能撤销外部系统中已泄露的凭据。

## 私有仓库与公开下载

私有 GitHub Release 需要权限，不能直接替换公开网站匿名下载链接。按用户选择在站点同域发布同一批批准文件，或选择明确授权的服务。不要把仓库改公开来绕过权限。

origin/base 必须有部署约定。域名根目录可用不代表子路径可用；安装指令 URL、下载链接和资源路径一起验证。临时签名 URL 只能用于本次传输，不能作为长期源码中的资产地址。

## 恢复验收

干净克隆使用远端已确认提交或标签，不依赖原机器输出、插件缓存或未跟踪文件。执行 README 命令后比较输出清单、正式媒体与下载附件。

固定 ZIP 时间戳、顺序和权限后，同一压缩环境应得到同一包；跨压缩库版本可用包内清单验证，不无依据地保证跨所有系统字节相同。

高清媒体的恢复需保留真正的生成原稿和加工参数。当前展示 WebP 与正式安装图集用途不同；从原稿实际重建并比较像素/字节，不能只验证复制成功。生图得到的透明主图作为生成原稿保存，不冒称确定性抠图结果。

下载包核验实际取得的字节。Git push、Release 创建、附件上传和网站部署分别回读各自结果。旧 QA 文档与当前结果区分标注。
