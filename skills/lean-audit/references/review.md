# 完成审查

完成标准：用户逐项决定过找到的多余内容，同意删除的已删除，`scan_diff.py` 的 `flags` 清空。

## 步骤

1. 确定范围、计划和原样文件。
   - 范围：一次只审一次改动，即一个 PR 或一次任务的提交。用户指定了提交区间就用它；没有指定时，有未提交改动就扫描工作区相对 `HEAD` 的改动，否则扫描 `$(git merge-base HEAD <默认分支>)..HEAD`。几周的累计改动输出太多，按 PR 拆开审。
   - 计划：用户给的计划、任务说明或 issue；没有就用对话里约定的需求。从中列出允许改动的路径。
   - 原样文件：脚本自动跳过 `vendor/`、`node_modules/`、`dist/` 等目录，压缩文件、锁文件、许可证文本，以及 `.gitattributes` 中标为 `linguist-vendored` 或 `linguist-generated` 的路径。其余原样收录的内容用 `--verbatim` 传入，例如收录的第三方技能、构建生成的数据、业务数据记录、配置备份。
2. 运行：

   ```bash
   python3 scripts/scan_diff.py --repo <仓库> [--range <a>..<b>] --files <允许的路径> [--verbatim <原样路径>]
   ```

   多个路径用逗号分隔，以 `/` 结尾表示目录。`summary` 给出改动文件数、跳过数和命中最多的文件；`review` 按强信号在前输出，默认最多 80 条，用 `--limit` 调整。
3. 核对 `flags`：计划外的文件、测试文件、检查脚本、哈希代码、静默吞错（空 catch、`catch` 后返回 `null`/`false`、`except: pass`）。计划里没有明确要求的就是多余。同一段吞错出现在多个文件里时，一并指出复制。
4. 判断 `review` 里的每一句：讲“是什么、怎么用”的保留；提醒、免责、进度或验证状态、改名与版本经过、在别处已经说过的内容，按 [规则](rules.md) 列为多余。`summary.top_files` 里命中集中的文件，先看它是不是不该进仓库的过程文件（简报、验收记录、对照报告）。然后把新增的文档通读一遍，词表漏掉的同类句子一并列出。
5. 看 diff 里脚本识别不了的结构问题：新增的抽象层、配置开关、独立服务、跨模块关联，兼容旧版本的分支，静默修正输入，重试包装，只有一个调用方的接口。
6. 交给用户一份清单：每项写 `文件:行` 或引原文，说明对应哪条规则，给出删除或改写后的内容。用户确认后再改，改完重新运行一次 `scan_diff.py`。
