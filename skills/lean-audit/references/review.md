# 完成审查

## 确定改动范围

- 从用户原话、已确认的计划和后续决定提取预期结果、约束和涉及的使用入口。对照项目规则与现有行为，明确哪些行为会变，哪些约束仍适用。
- 根据需求和实际依赖列出允许修改的路径，供 `--files` 使用。需要扩大范围时，指出对应的要求或依赖。独立改进由用户决定。
- 有多种解释且会影响交付行为时，先用已确认的要求和项目规则判断。仍需用户决定的部分等确认，继续处理范围明确的工作。

## 审查步骤

1. 确定范围、计划和原样文件。
   - 范围：一次只审一次改动，即一个 PR 或一次任务的提交。用户指定了提交区间就用它；没有指定时，有未提交改动就扫描工作区相对 `HEAD` 的改动，否则扫描 `$(git merge-base HEAD <默认分支>)..HEAD`。几周的累计改动会产生太多输出，按 PR 拆开审。
   - 计划：以 [确定改动范围](#确定改动范围) 得出的要求和路径为准。事后审查时从实施前的要求重建范围，并纳入用户后来明确同意的调整。
   - 原样文件：脚本自动跳过 `vendor/`、`node_modules/`、`dist/` 等目录，压缩文件、锁文件、许可证文本，以及 `.gitattributes` 中标为 `linguist-vendored` 或 `linguist-generated` 的路径。其余原样收录的内容用 `--verbatim` 传入，例如收录的第三方技能、构建生成的数据、业务数据记录、配置备份。
     审查前读该仓库的贡献规则（CONTRIBUTING、AGENTS 等），把其中要求原样保留的内容（归档的上游源码、原文快照、由构建同步的副本等）用 `--verbatim` 传入。
2. 运行：

   ```bash
   python3 scripts/scan_diff.py --repo <仓库> [--range <a>..<b>] --files <允许的路径> [--verbatim <原样路径>]
   ```

   多个路径用逗号分隔，以 `/` 结尾表示目录；`--verbatim` 也支持含 `**` 的 fnmatch 模式。`summary` 给出改动文件数、跳过数和命中最多的文件；`review` 把强信号排在前面，默认最多 80 条，用 `--limit` 调整。
3. 核对 `flags`：计划外的文件、测试文件、检查脚本、哈希代码、静默吞错（空 catch、`catch` 后返回 `null`/`false`、`except: pass`）。用 [判断规则](rules.md) 逐项核实。同一段吞错出现在多个文件里时，一并指出。
4. 判断 `review` 里的每一句：讲“是什么、怎么用”的保留；提醒、免责、进度或验证状态、改名与版本经过、在别处已经说过的内容，按 [规则](rules.md#文档与界面文案) 判断。仓库规则要求保存的记录按其中的交付物条款处理。对 `summary.top_files` 里命中集中的文件，先区分交付记录与过程叙述，再把新增的文档通读一遍，词表漏掉的同类句子一并列出。
5. 逐项检查实际新增、修改和删除的行为。每项都对应一条已确认的要求，或指出缺少它会在哪条使用路径上影响交付。扫描结果为空时也要做这一步。
   - 涉及界面时，核对呈现的内容、位置、有无重复，以及同一功能在不同入口或状态下的表现。
   - 涉及业务规则时，核对纳入条件、计算范围和结果，确认受影响的原有调用和约束得到满足。
   - 涉及代码结构时，核对抽象、开关、依赖、兼容分支和兜底是否服务当前的需求与调用方。
6. 报告超出范围或需要用户决定的改动。每项给出 `文件:行` 或原文、实际影响和建议处理方式。按用户授权处理。调整后重新运行 `scan_diff.py`，并复核受影响的行为。
