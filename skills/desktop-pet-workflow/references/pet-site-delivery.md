# 宠物网站源码、下载与发布

用于宠物下载和 Agent 安装入口、网站源码整理、固定链接，以及已授权的页面发布。目录与版本遵循[Git 作品仓库](repository-and-release.md)，这里补充宠物网站特有的资源和安装关系。

## 保存完整网站

从实际页面依赖和现有构建步骤确认完整内容：HTML、样式、脚本、图片、动画、帧布局等运行数据与下载文件。有些文件曾由构建时复制或生成，删除旧处理程序前先把运行时需要的内容带齐。

将这些内容保存在 `site/` 并纳入同一作品仓库。网站初次保存和后续更新都提交到 Git，提交只包含这次确定的网页变化；原始素材属于 `pets/`，页面实际使用的资源属于 `site/`，允许保留清楚的副本关系。

纯静态页面直接保存完整目录。确实使用框架的站点保留它必要的依赖、锁文件和构建配置；精简仓库不等于删除仍被源码需要的东西。无需为普通静态网站增加额外构建系统。

网站与宠物分别维护。更新某款宠物不自动构成更新或部署网站的授权；用户同时要求更新网站时，对齐页面名称、预览、资源、下载与安装元数据。

清理本机绝对路径、内部账号或部署身份、凭据、临时链接和缓存，保留公开参考与作者署名。仓库可以私有，网站访问范围则遵守原有设置和本次要求。

## 两种入口使用同一份成品

为桌宠提供 Agent 安装与手动下载时，两者指向同一份已核对的原始便携包。安装卡片用明确名称和相应角色预览说明对象，主次顺序按用户选择；用户偏好 Agent 安装时，将其作为主要入口。

安装指令根据实际 ZIP 清单生成，包含可访问的下载地址、准确包内目录、README 与配置路径，以及有用途的最终包和原图校验值。作品改名、包结构或说明变化后，更新相关元数据，不套用另一款作品的旧路径。

指令引导接收端下载、解压、阅读实际说明，并通过当前目标应用支持的方式导入。跨账号不复用来源宠物 ID；默认导入后保持原有启用项，只有用户选择时才切换。

复制成功只能表示指令已复制，下载成功只能表示取得文件，实际安装需要目标应用返回或读回结果。公开页面若无法匿名下载私有 Release，应选择已授权的站内资源或明确的认证方式。

## 固定地址与缓存

站内可采用 `downloads/pet-name-portable.zip` 这样的固定文件名。页面使用相对地址，向 Agent 提供绝对链接时以页面 base URL 解析，兼容域名根目录与子目录部署。

更新同名 ZIP，并同步名称、作品版本、包内路径和实际校验值。站点部署完成后链接可保持不变；只发布 GitHub Release 并不会更新网页下载目录。

GitHub `releases/latest/download/<asset-name>` 选择仓库最新的一次发布，附件名不会触发逐作品寻找最新版。多个作品独立发版时，可用站内固定文件或明确版本的 Release；需要自动查询时再按用户目标设计，不顺带引入服务或改变仓库可见性。

素材改变后更新相应缓存标识，并确认页面实际加载的新资源。原有高清图、动作条带与安装元数据应避免新旧版本混用。

## 历史与 README

README 先介绍网站和作品、展示实际截图，再提供访问或源码入口。网站截图来自当前页面，至少选择能看清首页与主要交互的位置。

Git 历史依据实际保存的版本组织。只有当前网站时，可以单独提交当前源码；缺失的网站版本不套用作品版本补造。用户只要求当前文档修改时，历史发布保持既定范围。

临时处理工具、测试报告和机器环境留在工作区。网站运行数据与必要框架配置仍属于源码的一部分。

## 发布完成的依据

确认本次授权的目标网站与访问范围，再使用当前环境的发布工具。已准备的源码包遇到传输失败时保留并检查状态，不因一次超时重做作品。

上传、保存版本与部署是不同阶段。未知结果先读取当前服务状态；持续同因失败时保留已完成源码，报告具体剩余步骤。

确认目标提交或源码、保存的版本和部署成功，再查看线上页面的主要交互、实际下载与缓存更新。源码推送、Release 上传、预览可见、网站上线分别表述；只要求整理源码时，交付完整文件即可。
