# 宠物作品与版本发布

作品展示型仓库以阅读、欣赏和保存创作成果为目的。参考、提示词、高清原稿和成品应容易找到。用户明确需要可复现加工项目时，再讨论配方、依赖、脚本和自动检查。

## 保存内容

每款宠物用完整、稳定的名称作为 `pets/` 下的目录，按实际资料组织制作记录、参考、动作提示词、高清素材与解包成品。制作说明直接关联动作思路和相应文件，保留角色出处及作者署名。README 首先展示形象、特点、动画、制作来源和下载入口。

原稿保留生成细节，正式图集保留最终选帧。中间图是否保留，取决于它能否解释创作或帮助后续修改。一次性整理程序、检查报告、全仓库指纹清单、机器配置和无关素材留在任务工作区。未来可从现有资料继续修图，无需默认承诺重新生成完全相同的像素。

## 版本与提交

按用户提供的真实版本资料建立对应提交。局部更新包只替换发生变化的动作，沿用前一版未改资料；缺失来源不补造提示词、作者或制作日期。提交可以在整理时创建，勿伪装成当年的开发记录。

一个宠物版本对应一个提交时，逐次更新该宠物；工作树保存各宠物在该提交下的状态，旧资料由 Git 历史保存。默认不再用 `archives/` 重复保存旧版本。多宠物仓库先确定发布分组，例如以 `v1.2-<pet-name>` 区分独立版本。名称描述作品与版本，无需加入“基线”“真实作品”等整理状态。

改写主线、标签与 Release 前核对用户授权和当前远端状态，保留本地恢复副本。已作出的决定不重复询问。推送使用预期旧值，操作结果不明时先回读。

## 成品与 Release

普通 Git 跟踪解包成品，Release 提供便携 ZIP。按用途保留正式图集、名称/描述/格式元数据、简短说明与所需预览。参考、原稿和提示词留在作品目录。

需要当前 ChatGPT sprite v2 的逐动作 GIF 时，九种状态各一张，十六方向可合为一张预览。其他协议先读其实际要求。作品版本和协议版本分别表达；项目约定的 pet.json 不冒称所有应用通用的官方标准。

原账号 ID、启用状态、本机路径、凭据、短期链接与上传会话不进入包。发布时确认附件对应所标版本、能够打开且包含所需内容；完成这些工作无需向作品仓库加入检查体系。

## 网站独立保存

网站可与宠物同仓库、独立提交，保存完整源码、媒体、运行数据与下载资源。纯静态 HTML/CSS/JS 可以直接保存完整网站目录。网站使用自己的作品资源副本是合理选择，不强制与 `pets/` 建立构建依赖。

动画帧布局、下载名称与安装信息属于页面实际使用的数据；重建清单和制作 QA 不属于运行资料。网站更新时同步自己的资源。

GitHub `releases/latest` 为仓库选择一次发布，不能按宠物名分别寻找最新版。稳定下载可以使用网站内固定名称的 ZIP；公开站点不能直接依赖私有 Release 的匿名下载。按用户选择处理资源同步，不为了固定链接额外建立未请求的服务。
