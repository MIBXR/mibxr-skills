# Git 作品仓库与版本发布

制作宠物及其网站时都要使用本文件，先建立 Git 和清楚的文件归属，再持续保存创作材料与成果。作品仓库以收藏和展示为主；用户明确需要可复现加工项目时才扩展为加工工程。

## 开始制作就建立 Git

先查看目标目录是否已受 Git 管理，读取工作区改动、最近提交和远端。沿用已有作品仓库，保留用户未提交和刚刚推送的内容，不覆盖或重新初始化已有历史。新项目在确定的作品根目录执行 `git init`，按当前约定设置主分支；避免意外落入上层无关仓库。

多个款式属于同一收藏时可放同仓库，已有独立仓库时沿用用户的分组。宠物网站通常置于同一作品仓库的 `site/`；它可以独立更新，不需要嵌套 `.git`，也不要求另开网站仓库。

从参考、主形象或第一份网页源码开始纳入版本管理。新创作按有意义的阶段提交，正式宠物版本各自形成提交；不等到完工时才把所有内容压成一个无法分辨过程的提交。提交前查看改动范围，只暂存本次作品文件，不顺带提交用户其他工作。

远端名称、所属账号和可见性沿用已明确的决定；尚未明确且需要发布时再对齐。已授权创建或推送就完成远端保存并回读结果；只有本地 Git 时如实说明它还不是远端备份。凭据、机器配置和临时下载地址不进入仓库。

## 围绕每款作品组织

新作品采用下面的结构，已有仓库按同样的职责维护。例子中的网页是纯静态形式，文件名以实际技术栈为准；没有网站或尚不存在的素材时不创建空目录占位。

```text
<collection>/
  README.md
  .gitignore
  pets/
    <pet-name>/
      README.md
      creation/
        README.md
        references/
        prompts/
      materials/
      package/
        README.md
        sprite.png
        previews/
  site/
    README.md
    index.html
    styles.css
    app.js
    assets/
    downloads/
```

| 位置 | 保存内容 |
| --- | --- |
| 根 `README.md` | 作品总览、所有宠物的动作画廊、来源、下载与网站预览入口。 |
| `pets/<pet-name>/README.md` | 这一款的形象、特点、全动作展示、创作资料和对应版本下载。 |
| `creation/README.md` | 制作来源、参考分工、各动作思路、实际制作说明及文件链接。 |
| `creation/references/` 与 `creation/prompts/` | 采用的参考图与实际使用的提示词；回顾说明与原始提示词分别标明。 |
| `materials/` | 采用的高清生成原稿，以及对继续修改有价值的关键素材。 |
| `package/` | 解包成品：正式图集、必要元数据、简明说明与逐动作 GIF；图集名和元数据格式以实际包为准。 |
| `site/` | 完整网站源码、实际使用的图片与动画、必要运行数据及下载文件；README 展示真实页面。 |
| `.gitignore` | 排除当前项目实际产生的依赖安装目录、缓存、临时产物、凭据和本机配置。 |

`package/` 中所有成品文件直接由 Git 跟踪。ZIP 作为 Release 附件，网站为下载服务保存同一 ZIP 的副本时放在 `site/downloads/`。不把资料先压成素材包才入库，不默认引入 Git LFS；如实际文件超过托管限制，再处理具体问题。

作品目录使用完整、稳定且能区分款式的名字，例如角色、服装、构图与风格的组合。名称直接介绍作品，版本号描述同一款的演进。术语以用户确认与参考为准，描述不凭空添加角色特征。

保留能解释当前作品或帮助继续修改的材料。缺失提示词、作者与制作日期如实标注，不把整理时写的回顾冒充原始调用或历史记录。一次性加工、打包和检查程序、依赖、运行报告、全仓库清单与缓存留在任务工作区；默认不添加 `tests/`、维护 `docs/` 或 `.github/workflows/`。网站确实需要的应用脚本、依赖声明和构建配置属于源码，仍放在 `site/`。

## README 是作品入口

首页先展示角色、特点和可以欣赏的内容，再提供制作来源、高清素材与下载。每款作品的全部动作都要容易看到，不能只展示待机与挥手就称为完整展示。

可用统一尺寸的动图画廊展示日常动作，给注视方向单独位置；每项配简短且符合成品的说明，提供清楚的替代文本与相对链接。单宠页、制作记录和包内 README 各自承担介绍、追溯与使用的职责。

有网站时加入真实页面截图、可用的访问入口或源码入口，截图来自当前页面。首页预览与动作交互区都可以展示，不能用设计草图代替已经完成的页面。

仓库简介、README 与实际文件保持一致。角色及插画来源、AI 辅助制作和后续整理分清署名。修正文案前先读取远端和工作区，保留用户刚改的内容，并检查其他介绍页是否有同样的旧表达。

## 一个版本对应什么

按真实提供的版本资料建立提交。只有局部更新的素材包，沿用上一版未变化的资料；不要将后来才出现的参考或提示词倒填成早期制作记录。

整理既有历史资料时，按一个宠物版本一个提交，每次只推进相应宠物。工作树保存各款在该提交下的状态，旧版由 Git 历史保存，通常无需另设 `archives/`。多个宠物版本相互独立，不因版本号相同就强行合并成一次提交或一次发布。

单宠仓库使用 `v1.0`、`v1.1` 这样的标签与 Release 名。同仓库有多款独立发布的宠物时，用 `v1.2-<pet-name>` 区分，附件采用清楚的作品名。版本名描述作品与版本本身；不把“基线”“历史归档”等整理过程写进作品标题。现有项目若已有用户认可的命名，沿用该约定。

每个版本的关系是：**该宠物的版本提交 → 指向该提交的标签 → 同名 Release → 从这一版成品取得的 ZIP**。网站后续提交不会改变这些标签。检查对应关系即可，无需为作品仓库增加自动打包或校验流水线。

提交可以在整理时创建，勿回填日期来伪装原来的开发记录。没有某段历史材料，就只记录可以确认的版本。网站若只有当前源码，可以单独提交当前网站，不套用宠物版本补造网站历史。

## 改动历史有明确范围

普通维护保留现有历史。用户要求只修订最新提交时，仅修改顶端提交并保留其父提交；已冻结的旧标签与 Release 是否改变，由本次授权单独决定。

改写主线或替换已发布内容前，核对现有授权、远端最新状态和本地恢复副本。推送使用预期旧值以防并发覆盖，结果不明时先回读。用户此前已作出的决定不重复询问。

## Release 与独立网站

Release 中提供对应版本的便携 ZIP。正式图集、必要元数据、逐动作预览与说明按[便携交付](delivery.md)组织；原稿、参考和提示词保留在仓库。发布后确认附件对应版本并能取得实际内容。

网站可以同仓库保存，但拥有自己的完整源码、媒体、运行数据与下载资源，可以独立提交和更新。它使用作品资源副本是合理选择，不强制从 `pets/` 构建。

网站初次制作和每次有意义的更新也要形成 Git 提交。按本次范围同步角色介绍、动作资源、包和安装信息；源码提交、推送和部署分别记录实际完成状态。网站的具体注意点见[宠物网站源码与下载](pet-site-delivery.md)。

GitHub 的 `releases/latest` 选择仓库的一次发布，不能通过附件名分别寻找每款宠物的最新版。固定下载可使用网站内固定名称的 ZIP，更新时替换文件并同步安装信息；仅发布 Release 不会自动更新网站。私有 Release 也不能当作匿名公开下载入口。
